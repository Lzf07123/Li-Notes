# 网页端与小程序共存方案

> 日期：2026-10-23 ｜ 状态：自动刮削与后台持久化已实现，待生产域名配置与真机验收
> 关联项目：Li&Notes（网页端）· Li&知识速查（微信小程序）

## 1. 目标

让完整笔记网页和离线速查小程序共享同一份内容事实，同时保持两端职责、交互和审核边界清晰：

- **Li&Notes 网页端**：完整文章、长文阅读、归档、标签、搜索和后台写作。
- **Li&知识速查小程序**：结构化命令/概念查询、复制示例、离线兜底和可审计的内容热更新。
- **唯一内容源**：不再手工维护两套速查数据。
- **可回退**：远程内容不可用时继续使用内置基线。
- **不绕审**：小程序代码仍走微信版本发布；只有结构化内容和图片允许热更新。

## 2. 产品边界

| 能力 | 网页端 | 小程序 |
| --- | --- | --- |
| 完整文章正文 | 是 | 否 |
| 文章归档/标签 | 是 | 否 |
| 速查分类与搜索 | 可选入口 | 是 |
| 命令/概念详情 | 文章页 | 专属速查页 |
| 评论/留言/注册 | 否 | 否 |
| 后台编辑 | 是 | 否 |
| 网络请求 | 公开页无 | 可读取版本化静态数据 |
| 内容更新 | 重建发布 | 内置基线 + 可选热更新 |

## 3. 推荐架构

```text
       content/posts/*.md + mini_json（唯一事实源）
                         │
             ┌───────────┴───────────┐
             │                       │
      Hugo 构建完整文章         knowledge 导出
      /posts/<slug>/           knowledge bundle
             │                       │
             │         ┌─────────────┴─────────────┐
             │         │                           │
             │   小程序内置基线                线上 manifest/JSON
             │         │                           │
             └──────► 公开站/小程序共用域名 ◄──────┘
```

### 3.1 内容源

不新增文章副本。每篇笔记仍是 `content/posts/<slug>.md`；需要进入小程序时，在 frontmatter 增加一个 `mini_json` 块标量：

```yaml
```yaml
---
title: 包管理-apt
date: 2026-05-24
status: published
mini_json: |-
  {
    "enabled": true,
    "items": [
      {
        "id": "apt",
        "category": "linux",
        "title": "APT 包管理",
        "command": "apt",
        "summary": "Debian / Ubuntu 新一代包管理入口",
        "keywords": ["安装", "卸载", "更新"],
        "tags": ["包管理", "Linux"],
        "syntax": "apt [选项] 操作 [包名]",
        "examples": [
          {"label": "刷新软件源索引", "code": "sudo apt update"}
        ],
        "notes": ["安装或升级前先执行 apt update。"],
        "related": ["apt-get", "dpkg", "flatpak"],
        "order": 10
      }
    ]
  }
---

apt 是 Debian / Ubuntu 系列常用的包管理入口。
```
```

- 正文只供网页阅读，不会进入小程序。
- `mini_json` 供构建期导出；后台编辑器提供 JSON 校验。
- 不使用 `web-view`，小程序只保留结构化条目和可复制的文章 URL。
- `related` 必须指向存在的速查 id。

### 3.1.1 自动刮削

手写 `mini_json` 仍受支持，但不再是新增速查的必要条件。构建时会按以下优先级处理：

1. `mini_json.enabled: true`：使用手写条目。
2. `mini_json.enabled: false`：永久跳过自动刮削。
3. 未配置：读取 `config/knowledge.yaml` 的 `auto_scrape` 规则，按分类匹配关键词确定分类。
4. 优先解析 `## 📋 命令速查` 表格；没有命令表时，从允许语言的代码块生成一篇一个条目的候选。
5. 自动候选只在后台确认后才写回 frontmatter，并标记 `generated_by: auto-scrape-v1`。

因此“唯一内容源”仍是文章 Markdown，但速查配置既可以是作者手写，也可以是后台确认后持久化的自动结果。构建期自动候选不写入运行期数据库，避免重启丢失或产生第二份不可审阅的配置。

### 3.2 网页端

- 文章仍只出现在 `/posts/`，不产生第二套文章页面。
- `/index/` 只聚合文章元数据，不复制正文。
- `mini_json` 对网页正文无影响，Hugo 只把它当作 frontmatter 数据。
- 小程序不镜像正文；需要原文时复制文章 URL 到浏览器。

### 3.3 小程序端

保留当前原生 WXML/WXSS/JS 结构，只替换数据加载层：

```text
data/cheatsheet.builtin.js   # 发版内置基线
utils/content-loader.js      # 缓存、manifest、校验、回退
data/cache-meta.js           # 当前缓存版本/哈希
```

启动流程：

1. 同步读取内置基线，立即渲染。
2. 后台请求 `manifest.json`，不阻塞首屏。
3. 比较版本和 `minAppVersion`。
4. 下载 JSON，做大小、schema、哈希和引用完整性校验。
5. 校验通过后写入本地缓存；失败保留旧缓存或内置基线。
6. 下次启动优先使用“最近一次校验通过”的缓存。

## 4. 导出产物

构建或发布时生成：

```text
output/knowledge/manifest.json
output/knowledge/v20261023.1.json
```

`manifest.json` 示例：

```json
{
  "schemaVersion": 1,
  "contentVersion": "2026.10.23.1",
  "minAppVersion": "0.2.0",
  "generatedAt": "2026-10-23T12:00:00+08:00",
  "count": 35,
  "sha256": "…",
  "dataUrl": "/knowledge/v20261023.1.json"
}
```

数据文件只包含：

- `schemaVersion`
- `contentVersion`
- `categories`
- `items`
- `generatedAt`

不包含后台凭据、个人资料、文章全文或可执行代码。

## 5. 热更新协议

### 5.1 允许更新

- 速查条目、分类、排序、关键词。
- 独立图片资源。
- 版本清单与最小小程序版本约束。

### 5.2 不允许更新

- WXML/WXSS/JS 页面代码。
- 动态执行远程 JavaScript。
- 绕过微信审核的页面/功能变更。
- 需要登录或收集访客信息的接口。

### 5.3 缓存策略

- 内置基线：永不删除，作为最终兜底。
- 最近成功缓存：最多保留 1 份。
- 失败数据：不覆盖成功缓存。
- 版本不兼容：忽略远程包，提示用户更新小程序。

### 5.4 安全校验

- 固定 HTTPS 域名并配置微信 request 合法域名。
- 限制下载体积（建议单包 ≤ 512 KiB，总缓存 ≤ 2 MiB）。
- JSON schema 严格校验，未知字段丢弃。
- `related` 引用完整性校验。
- 文本字段禁止 HTML/脚本片段。
- 服务端生成 SHA-256，客户端比对。
- 每次发布保留旧版本文件，支持回滚。

## 6. 仓库与发布策略

### 阶段 A（推荐先做）

保持现状：

- Li&Notes：网页内容源与后台。
- `~/WeChatProjects/miniprogram-1`：独立小程序工程。
- 新增 `scripts/export_knowledge.py`，从 Li&Notes 导出小程序数据。
- 小程序把导出结果作为内置基线，同时读取线上 manifest。

优点：不打断当前发布和微信开发者工具工程。

### 阶段 B（稳定后可选）

把小程序迁入同一仓库：

```text
apps/web/
apps/miniapp/
content/
packages/knowledge-schema/
```

优点：一次提交同时验证两端；缺点是迁移成本和微信开发者工具路径变化。

不建议用 git submodule 共享速查数据；数据是构建产物关系，不应当靠子模块同步。

## 8. 当前实现进度

- 文章编辑器支持 `mini_json` JSON 配置，并做 schema、示例、标签和引用校验。
- `config/knowledge.yaml` 管理分类、简介、符号和最低小程序版本。
- `--full` 构建自动输出 `output/knowledge/manifest.json` 和版本 JSON。

## 9. 验收标准

- 网页端文章与速查页由同一份 Markdown/YAML 生成。
- 小程序首次安装可离线使用内置基线。
- 远程内容更新后无需重新发版即可生效。
- 断网、空响应、坏 JSON、哈希不符、版本过低均回退到最近成功缓存或内置基线。
- 小程序不读取微信身份，不上传搜索词或用户数据。
- 小程序代码仍通过版本上传和审核发布。
- 两端内容版本可追溯，支持回滚到上一内容版本。

## 10. 风险与约束

| 风险 | 处理 |
| --- | --- |
| 微信审核认为远程内容不可控 | 只做工具查询；不承载资讯流、文章镜像或用户内容 |
| 个人主体不能使用 web-view | 不放文章正文；需要原文时复制站内 URL |
| 远程请求失败 | 内置基线与最近成功缓存双兜底 |
| 数据格式漂移 | schema 版本 + 导出校验 + 双端测试 |
| 包体积膨胀 | 只打包精选速查，不打包文章图片与全文 |
| 图片域名/证书故障 | 图片可选、失败占位、文本功能不受影响 |
| 两仓库版本不同步 | 导出脚本把内容版本写入 manifest；小程序检查兼容版本 |

## 11. 结论

推荐采用**“同一内容源、两种呈现层、内容热更新但不做代码热更新”**的方案：

- Li&Notes 继续做完整文章网页和编辑后台。
- 小程序只做结构化速查和阅读辅助。
- 用文章 Markdown + `mini_json` 单一事实源生成两端产物。
- 小程序保留离线基线，远程 manifest 只更新内容。
- 本阶段先完成 Li&Notes 文章域分离，再实施导出脚本与小程序加载层。
